# v1.1 Cross-sectional Research Store acceptance

## Deployment

The new empty database is at
`user_data/research/alpha_lab/stores/v1.1-cross-sectional/experiments.sqlite3`.
It is a separately provisioned SQLite file and was not copied from or migrated
from the historical database. The immutable store identity row declares:

| Field | Value |
|---|---|
| Store ID | `alpha-lab-v1.1-cross-sectional-store` |
| Schema version | `1.1.0` |
| Role | `cross-sectional-v1.1` |
| Historic DB SHA-256 at provision | `f92010447c34d24a293d71693c75950aef45cd4f955310c648929a6d89ad6cf9` |

The existing engine data model is retained: `experiments` remains the parent
run registry; `cs_evaluations.run_id` and `cs_research_decisions.run_id`
reference it. The additional `alpha_lab_store_identity` table is deployment
metadata only; it does not contain or alter Evidence or Decision payloads.

`cs_evaluations` has primary key `run_id`, required `config_hash`,
`evidence_hash`, canonical `payload_json`, and `created_at`, plus
`idx_cs_evaluations_config(config_hash)`.
`cs_research_decisions` has primary key `decision_id`, required Run and
source identity, supporting/opposing evidence, conclusion, next hypothesis,
next actions, optional agent identity, and creation time, plus
`idx_cs_decisions_run(run_id, created_at)`. Both tables have UPDATE and
DELETE abort triggers. Run identity is established by the existing registry's
immutable run ID/config/time/code/data fields and one-way running-to-completed
or failed transition.

## Acceptance evidence

Command:

```text
/home/von/workspace/venv/bin/python scripts/alpha_lab_store_acceptance.py --conformance
```

The conformance test used disposable files and synthetic-only payloads. It
verified both CS tables, both indexes, one Run foreign key per CS table,
`integrity_check=ok`, empty `foreign_key_check`, duplicate append idempotence,
conflicting evidence rejection, Decision rejection for an unknown Run,
reopen stability, and actual UPDATE/DELETE rejection on a separate SQLite
backup copy. No synthetic rows were written to the deployed empty Store.

Deployment path SHA-256 at creation:
`6725867cfb024d19c7f3e888d102fe18374c87c746654667466628d50b42a9da`.
Historical path SHA-256 before and after deployment/conformance:
`f92010447c34d24a293d71693c75950aef45cd4f955310c648929a6d89ad6cf9`.

The separate acceptance harness validates deployment identity, schema, indexes,
foreign keys and integrity, then performs the disposable conformance test. The
existing `scripts/alpha_lab_admission_gate.py` itself remains unchanged because
its hash is recorded as the Panel builder; its current Store check still relies
on trigger names/SQL text. Consequently that existing Gate cannot be cited as
passing append-only enforcement. The new acceptance harness establishes actual
mutation rejection independently; integrating it into the Gate belongs to the
pending frozen-version migration below.

## Decision

**Store component: PASS for isolated schema and synthetic append-only
conformance. End-to-end Agent/Gateway/Runner admission: BLOCKED.**

At this HEAD, `research_agent_cli.py` and `cross_sectional_runner.py` still
hard-code `user_data/research/alpha_lab/experiments.sqlite3`; they do not read
the new Store ID or versioned path. Changing those frozen modules requires a
separate `ENGINE_CHANGE_REQUEST`, a versioned engine/protocol identity, failing
regression coverage, Golden comparison, freeze update and Maintainer/CODEOWNER
review per the repository's v1.1 process. A concrete request is recorded in
[`ENGINE_CHANGE_REQUEST-v1.1-store-selection.md`](ENGINE_CHANGE_REQUEST-v1.1-store-selection.md).
No approval/review record was present in this checkout, so integration was
deliberately not performed. The new DB must not be described as selected by
the Gateway or Runner until that migration has passed review.
